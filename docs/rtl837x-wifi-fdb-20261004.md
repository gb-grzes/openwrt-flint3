## Cause and implementation

`net/dsa/user.c:dsa_user_fdb_event()` ignores dynamic foreign bridge entries
unless the switch requests `assisted_learning_on_cpu_port`. This driver
did not request it. In addition, RTL8372N's CPU `port_fdb_add` callback was
an unconditional no-op. Unknown unicast already floods to the CPU, but
a stale known destination remains on its old physical port.

The existing VID helper also always selected a tag_8021q internal VID for
software VID 0. Native `rtl8_4` does not use those VIDs: its untagged layout
is the seeded hardware VLAN 1.

The change is deliberately limited:

1. Request assisted bridge learning for RTL8372N only. DSA now reports a MAC
   newly learned on Wi-Fi or another foreign port in the same bridge.
2. Map VID 0 to VLAN 1 under native rtl8_4. Preserve explicit VIDs and the
   existing tag_8021q database helpers in the fallback mode. Both physical
   port add/delete callbacks use the same mapping.
3. In the RTL8372N CPU add callback, look up only that MAC/VID key. Remove
   it only if it is dynamic, on a valid user port, and that port belongs
   to the reported bridge. Preserve static entries, other bridges, private
   host addresses and entries already directed at the CPU.

The membership check and SDK operation are serialized with bridge
join/leave using the existing isolation mutex. SDK lookup/delete errors
are returned to DSA; a missing key is harmless.

This retains the chip's existing unknown-unicast-to-CPU design rather than
installing new static CPU entries. Its CPU delete callback therefore remains
a no-op: it must not delete an address already relearned on a returning LAN
client. DSA handles the shared-port notification reference counting.

There is no client MAC in the production code, periodic flush, userspace
hotplug workaround, register poke, new kernel patch, tag-protocol change,
PPE/offload policy change, or change to Wi-Fi, MLO, LEDs or country settings.

DSA describes foreign-address notification in its
[host address filtering documentation](https://www.kernel.org/doc/html/latest/networking/dsa/dsa.html#host-address-filtering).
The version-specific implementation was checked against the local 6.18.52
source (`net/dsa/user.c`, `net/dsa/switch.c`, `net/bridge/br_fdb.c`).

## Verification

Run the host-only tests without a router connection:

```sh
bash package/kernel/rtl837x/tests/test-fdb.sh
```

The test compiles the actual production FDB functions, extracted from the
driver, against an SDK/DSA model with warnings treated as errors. Thirteen
groups passed: native/fallback VID selection, one-key removal, idempotence,
explicit VLAN separation, static-entry preservation, bridge/standalone
boundaries, CPU/invalid ports, private addresses, return to LAN, SDK errors,
user-port key symmetry, invalid arguments and the other-chip add path.
These are simulations, not ASIC or on-router tests.

Cross-build the kernel package:

```sh
make -j2 package/kernel/rtl837x/compile V=s
```

The first build attempt hit the sandbox's local-socket restriction in
fakeroot while packaging a dependency. This is unrelated to the C change.
The retry completed successfully: the ARM64 module linked, passed MODPOST,
and the release-3 kernel package was generated. The build emitted no C
compiler warnings for the changed driver; MODPOST reports the existing
missing `MODULE_DESCRIPTION()` in this driver and gpio-button-hotplug.
Dependency packaging also reports unselected crypto-kpp/fs-netfs modules.
The `.config` SHA256 was unchanged before and after the build:
`a0f5d31055c39c930129f53eba0579f69094ecfdfb58c5466220d9716ea4f999`.

The retry log is recorded outside the repository in
`/home/grzesiek/Documents/Codex/flint3-dhcp-diag-20261003/rtl837x-fdb-build-20261004-verified.log`.

## Required hardware validation after a full image build

Do not run the old deleting diagnostic again to validate this patch: it
would mask whether the driver handles the move by itself. Use read-only
FDB/station/DHCP capture and the original Aspire MAC/profile.

- After installing the new image, verify LAN and management access first.
- Move Aspire TP-Link -> ordinary Flint 5 GHz repeatedly. DHCP and access
  to Flint/gateway/internet should work without manual FDB deletion. The
  old hardware LAN2/VLAN-1 entry should disappear after learning on Wi-Fi.
- Return to TP-Link and verify DHCP/traffic and normal LAN2 relearning.
- Repeat separately with the MLO SSID's 5 GHz link; keep a recovery path.
- Recheck wired LAN-to-LAN traffic, explicit VLANs/guest isolation and
  kernel messages for FDB SDK errors. Runtime tagger switching and
  multi-bridge hardware behavior have not been tested on this router.

No firmware was flashed and nothing was pushed to GitHub during preparation.
